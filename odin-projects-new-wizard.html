New Project Wizard notes

  • Three steps shown together on this mockup page so reviewers see the full flow at once. In production, only one step is visible at a time and the stepper at the top tracks progress.
  • Replaces Mandeep's existing four-step wizard. Steps 3 (Deliverables/Tasks) and 4 (Report folders) from the current production version are removed entirely. Tasks happen in the Tasks tab now with full hierarchy and est-vs-act tracking; report folders concept is replaced by the new tab structure.
  • Pre-populated demo data shows a realistic state. Empty form would have all fields blank.
  • "Save as draft" is available on every step. Lets the PM walk away mid-setup without losing what they've entered. Draft projects appear in the Project List view with a draft badge until completed.

Step 1: Project basics

  • Project ID is now optional. Per Justin's May 28 confirmation, ID comes from Jonas and may not be known at project creation time. Helper text "assigned in Jonas, can be added later" sets the expectation. The actual unique identifier is the internal database ID; Project ID is a human-readable accounting reference.
  • Add Client inline button retained from the Mandeep version. Lets the PM create a new client record without leaving the wizard. Opens a small modal (not mocked).
  • Public/Private toggle removed. Per Justin's confirmation, Thor's culture is "everyone sees everything"; the toggle was paying rent for a case that almost never happens. Database can retain a visibility column for future flexibility; UI doesn't expose it in v1. If Thor ever needs project-level privacy, that's a v2 addition.
  • Dates & Labor budget grouped in a blue-tinted section to signal it's the contractually meaningful block. Total labor estimate is the new field per Justin's May 27 confirmation; it's the headline number for the project's Tasks tab budget rollup.
  • Labor estimate helper note explicitly says "you'll break this down into tasks later." Important to prevent the PM from feeling like they have to define all tasks now. The Tasks tab is the right place; the wizard sets only the total.

Step 2: Team

  • Structurally same as Mandeep's existing step 2. Search-and-add pattern is good; no need to rework. Just brand swap and a few clarifications.
  • Roles list trimmed to four (D-034, per Mike + Thor PMs): Project Manager, Supervisor, Foreman, Technician. The earlier production set (Site Manager, Engineer, Inspector, Coordinator, Estimator) was cut: the module only needs the roles that map to a project responsibility and to the mobile composers (Supervisor, Foreman, Technician) plus the PM. Project Manager, Supervisor and Foreman are the Project Leaders on the Overview Team card; Technician is the field role.
  • Default Team Members pre-load from the Default Team admin setting (Kyle Steele and Adam Coey in this example, marked with green "Default" pills). PM can remove or supplement.
  • Helper text reflects Thor's open access culture. Per Justin: all employees see all projects regardless of team membership. The Team list is for assignment dashboards, notifications, and tech mobile "Projects" widgets, not for access control.

Step 3: External contacts (the new step)

  • Replaces both the old "Deliverables / Tasks" step 3 and "Report folders" step 4. External contacts is genuinely new functionality required by the RFI compose-and-send flow (section 6.6.5).
  • Repeating-row composer. Each contact is a card with name, organization, email, phone, role dropdown. Add another via the dashed-border button at the bottom.
  • One contact marked "Primary GC" with the amber star treatment. Default recipient when the PM raises an RFI. Other contacts available as alternatives in the typeahead.
  • Set as Primary affordance on non-primary cards. Click to promote.
  • Roles list: General Contractor, Engineer of Record, Architect, Owner / Building Representative, Subtrade Lead, Inspector / AHJ, Other. Open to expansion if Justin or PMs need additional roles. Architect and Inspector aren't always RFI recipients but worth capturing for project records.
  • Skip-able. If the PM doesn't have contact info at creation, they can hit Create Project without adding any. Empty state shown as a separate state on this mockup page. Contacts can be added later from Edit Project.
  • Fallback when no contacts exist: the RFI compose recipient field falls back to free-text only, no typeahead. Project still works.

Edit Project derivative

  • Same fields, different UI mode. Edit Project takes the same data model and renders it as a single sectioned form with no progress indicator. Sections collapse and expand for navigation; Save button at the bottom commits all changes.
  • External Contacts section on Edit Project is the most common path for adding GC contact info after the project is already running. Most PMs will skip this step in the wizard and come back later, so the Edit Project version of this section is the workhorse.
  • Mocked separately as odin-projects-edit.html.

Data model implications

  • Project entity gains total_labor_estimate_hours (numeric, nullable) and external_contacts (jsonb array). Already specced in section 10.
  • External contact object: name, organization, email, phone, role (enum), is_primary_gc (boolean, only one true per project).
  • Project ID remains required at the database level but UI-optional during creation. Backend can auto-assign a placeholder (e.g. "DRAFT-XXX") until the real Jonas number is added.

Out of scope

  • Importing contacts from a company-wide directory (v1 keeps contacts project-scoped per spec section 6.6.9)
  • Duplicate detection across projects ("This contact also exists on Project X")
  • Sending welcome emails to newly-added team members or contacts
  • Project templates ("Create new from previous project") parked for v2
